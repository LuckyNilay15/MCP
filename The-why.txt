The arrival of LLM:
Mode change from transactional to transformational.

The problem of fragmentation:
We have different AI worlds.

Vision: Unified AI agent.
Challenge: The problem of context.

What is context?
Knowledge /Information + Memory  avaliable to the agent.

What is the problem?
Context is scattered.----> lead to copy-paste hell.

The solution: Function calling.
OpenAI introduced function calling.

Function calling is a mechanism that allows an AI agent to call functions in order to perform a task.

LLM -------> tool1---> weather api
            tool2---> news api
            tool3---> databases
            tool4---> file system

====> The implication of function calling--->tools----> integration become easy.

====> The implication of integration--->context become easy.

====> The implication of context--->agent become easy.

====> The implication of agent--->unified AI agent.

The new scenario:
Context assembly problem has been solved.

Problem with tools:

1.Integration problem.

N chatbot.   m software====> n*m integration.

since,
different authentication methods
different data formats and api patterns
different data access methods
different data storage methods
different error handling.

2. Maintenance problem.

3. Security fragmentation.

4. Cost and time wastage.

Overview of the problem:

Every AI tool was buidling its own way to call every API.

The solution:

The source build a tool which can be integrated by any AI tool.

MCP Client SDK              MCP Server SDK

##MCP Vs Function/Tool Calling:

1.General Function Flow:

Client :
function_call to call server take response and process it and display to end user.
The function called is the function of the server which takes input queries the db 
take out relevant data and return it to the client.

2. Now just server code written in a way so that logic is same
and the configuration is passed to the client SDK 
Now client SDK will call the server SDK and get the response.

result=call_tool("tool_name",input)

So, here Server does the heavy lifting.

Lets say Github server:
Authentication with github
API rate limiting
Data format translation
Error handling
Github specific business-logic.

Client just has to connect to the server.

Benefits:

N Client + M Server===> M + N integration instead of M*N integration.
All the logic writting part has been delegated to the server instead of client.
No maintenance overhead.
Reduced cost and time.
Better Security.

***Note: In the configuration, we can define the authentication method, data format, api pattern, etc for the particular tool(thats it).

Now to manage this single file is much easier than n files.
